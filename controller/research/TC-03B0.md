# TC-03B0 — untouched-build reproduction receipt

Status: portable build-handoff contract only. Target remains the 2027-28 Terps Racing EV torque-control project.

## Decision

Before any source-specific instrumentation patch is prepared, retain an explicit receipt for the untouched firmware build. A zero exit code by itself is not sufficient evidence: the receipt must bind the exact source commit, clean source state, exact working directory, exact declared and executed build command, toolchain identity/version, output logs by digest, and produced artifact hashes/sizes.

This pass does not reproduce the Terps Racing build because the authorized firmware repository, exact revision, toolchain, and build command are not available in this ChatGPT-side context.

## Source-state contract

The recommended source preflight is:

- verify the requested revision as an actual Git commit object, not a branch nickname;
- record the exact observed commit;
- record `git status --porcelain=v1` and require it to be empty for an untouched-build baseline;
- if submodules exist, record recursive submodule status and reject uninitialized, mismatched, or conflicted submodule states;
- retain the exact evidence-packet digest used to authorize the reproduction.

Git's current `git rev-parse` manual documents `--verify` plus `^{commit}` as a way to require a name to resolve to a commit object. Git's `status --porcelain=v1` format is explicitly guaranteed not to change incompatibly across Git versions or based on user configuration, which makes it suitable for a machine-readable clean-tree receipt. `git submodule status --recursive` reports the checked-out commit and marks uninitialized, mismatched, and conflicted submodules with `-`, `+`, and `U`.

These commands establish repository state, not firmware correctness.

## Build receipt

The portable v1 schema records:

- target car label `2027-28`;
- SHA-256 of the exact TC-03A evidence request used for the handoff;
- expected/observed 40-hex Git commit;
- commit-verification result;
- raw porcelain-v1 worktree/index status;
- raw recursive submodule status;
- declared and observed working directories;
- declared and executed build commands;
- build exit code;
- SHA-256 of stdout/stderr bytes;
- toolchain executable and exact version text;
- one or more normalized relative output-artifact paths, SHA-256 digests and byte sizes;
- explicit confirmation that no hardware access, flashing, or vehicle actuation occurred.

`evidence_complete=true` means only that this build-only receipt is internally complete under the contract. It does not establish independent review, embedded runtime behavior, safety, rule compliance, deterministic toolchains, or authority to flash hardware.

## Repeat-build comparison

The companion comparator only calls two receipts comparable when source commit, evidence packet, command, working directory and toolchain identity/version match. If the same artifact paths then hash identically, it reports byte-identical output.

Artifact drift is preserved as evidence rather than hidden. A non-byte-identical build may come from timestamps, archive ordering, absolute paths, toolchain behavior, generated metadata, or a real source/environment difference. TC-03B must investigate it before relying on binary-size or instrumentation comparisons.

GitHub's artifact-attestation documentation follows the same provenance principle at a stronger signed-workflow layer: provenance links an artifact to source/build context, but GitHub explicitly warns that an attestation does not prove that the artifact is secure. This local ENME408 handoff does not require adding GitHub Actions or a signing service.
