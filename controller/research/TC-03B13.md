# TC-03B13 — timer auto-reload modulus and wrap-safe freshness

Accessed 2026-10-02. Target remains the 2027-28 Terps Racing EV torque-control project.

## Decision

Do not infer a timer timestamp's wrap modulus from register width alone.

For an STM32F405 general-purpose/basic timer used as a simple up-counting timebase, the active hardware sequence is determined by `TIMx_ARR`: the counter runs from 0 through ARR and then restarts at 0. Therefore the timestamp modulus is `ARR + 1`, not automatically `2^counter_width`.

That distinction closes a real gap between TC-03B11 and the existing portable `timebase_freshness.py`. The existing helper deliberately hard-codes a 32-bit `2^32` modulus. It is valid only for a source-specific timestamp that really wraps that way. It must not be reused unchanged for:
- TIM3/TIM4/TIM6/TIM7/TIM9–TIM14, which are 16-bit on STM32F405;
- a TIM2/TIM5 timebase whose ARR is configured below `0xFFFFFFFF`;
- a 16-bit timer whose ARR is configured below `0xFFFF`;
- a down-counting or center-aligned timer;
- a software overflow-extended timestamp unless that extension has its own atomicity/race evidence.

## Primary-source findings

ST DS8626 Rev 12, March 2026, was inspected directly in this pass.

Table 4 on PDF page 34 shows:
- TIM2 and TIM5: 32-bit;
- TIM3 and TIM4: 16-bit;
- TIM9–TIM14: 16-bit;
- TIM6 and TIM7: 16-bit;
- TIM1/TIM8 are 16-bit advanced-control timers.

The following datasheet page states that TIM2/TIM5 are based on a 32-bit auto-reload up/downcounter, while TIM3/TIM4 use a 16-bit auto-reload up/downcounter; TIM9–TIM14 are 16-bit auto-reload upcounters; TIM6/TIM7 may be used as generic 16-bit timebases.

ST RM0090 is currently Rev 22, May 2026. Its general-purpose timer behavior states that in up-counting mode the counter counts from 0 to the auto-reload value and then restarts from 0 at overflow. The current revision pin matters, but this arithmetic does not rely on a Formula SAE rule.

## Portable ordering rule

For a stable up-counter with modulus `M = ARR + 1`:

`delta = (now - sample) mod M`

This alone does not order all pairs. To distinguish "sample is in the recent past" from "sample appears in the future after wrap", the accepted age threshold must stay inside the unique half of the ring.

The portable gate therefore uses:

`maximum_unambiguous_age_ticks = floor((M - 1) / 2)`

For an even modulus, an exact `M/2` separation is explicitly ambiguous. A configured `max_age_ticks` larger than the unambiguous half-range blocks review.

This is a mathematical ordering contract, not a firmware safety proof.

## Frozen counterexample

Synthetic timer: 16-bit TIM3, 1 MHz, ARR=999.

Hardware modulus:
- `M = 1000` ticks;
- full wrap = 1 ms;
- maximum unambiguous recent age = 499 ticks.

Sample at 990, now at 10:
- correct ARR-aware age = `(10 - 990) mod 1000 = 20` ticks;
- a naïve 16-bit mask produces `(10 - 990) & 0xFFFF = 64556`.

The mask result is wrong because the hardware did not count through 65535; it wrapped at ARR=999.

The same configuration cannot support a 100 ms raw-counter freshness threshold. At 1 MHz that requirement is 100,000 ticks, far beyond the 499-tick unambiguous recent-age window. A source-specific implementation would need a longer timer period, slower counter rate, a wider timer, or a reviewed overflow-extension scheme.

## Portable reference

`counter_modulus_gate.py`:
- binds the STM32F405 timer identity to its documented 16/32-bit width;
- requires a simple up-counting mode;
- derives modulus from ARR+1;
- validates sample/now ticks against active ARR;
- rejects thresholds outside the unambiguous half-range;
- classifies fresh, stale, future and exact-half-range ambiguous states;
- freezes the "bit-width mask is wrong when ARR is smaller" counterexample;
- rejects overflow-extended timestamps because that needs a different evidence model.

It deliberately does not prove overflow ISR atomicity, cross-domain equivalence, WCET, independent review, or vehicle acceptance.

## Source-specific worker packet

Prerequisites:
1. TC-03A identifies the real firmware/timer source.
2. TC-03B0 reproduces the untouched build.
3. TC-03B11 binds the nominal timer tick rate.
4. TC-03B12 binds the frequency interval if a real-time threshold depends on clock accuracy.

Ordered actions:
1. Identify the exact timestamp source used by each freshness/persistence check.
2. If it is a TIMx counter, record the exact TIM instance, counter mode, active ARR and PSC.
3. Confirm whether ARR/PSC/mode can change during the evaluated window.
4. Derive the actual modulus as ARR+1 for a simple up-counter.
5. Convert the requirement into ticks in the correct conservative direction from TC-03B12.
6. Require that the resulting maximum-age/persistence ordering window fits inside the counter's unambiguous half-range.
7. If the requirement does not fit, do not stretch the half-range rule. Change the source-specific design only after team review: use a longer period/slower tick/wider timer or prove a software overflow extension.
8. If overflow extension is used, separately verify overflow accounting, read/update atomicity, race behavior at rollover, ISR priority/timing and reset behavior.
9. Keep cross-domain timestamps separate unless a reviewed mapping exists.
10. Preserve raw counter, ARR, PSC, mode and derived age in debug logs for bench review if the team authorizes that instrumentation.

Stop conditions:
- timer identity or ARR is unknown;
- source uses down/center-aligned counting but freshness logic assumes monotonic up-counting;
- ARR/PSC can change but the transition is unmodeled;
- threshold exceeds the unambiguous half-range;
- an overflow-extended counter is accepted without race/atomicity evidence;
- validation would require unapproved flashing or vehicle actuation.

No firmware flashing, CAN transmission, HIL, dyno, track testing, watchdog/shutdown changes, Company Runtime mutation, or vehicle actuation is authorized.
