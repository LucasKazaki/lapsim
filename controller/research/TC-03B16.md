# TC-03B16 — timebase pause/reclock continuity and epoch invalidation

Accessed 2026-10-03. Target remains the 2027–28 Terps Racing EV torque-control project.

## Decision

After clock-rate, timer-modulus, overflow-service, and update-source evidence, add one more gate before a timestamp can support a source-specific freshness/timeout claim:

> prove that every reachable execution mode either preserves the timebase continuously at the reviewed rate, or explicitly invalidates pre-transition timestamps by moving to a new epoch.

A nominal frequency and correct wrap formula are insufficient when the counter can pause, reset, or change rate.

This closes a gap between the existing TC-02D/TC-02E freshness contracts and TC-03B12–TC-03B15 timer-source work.

## Current primary-source findings

ST's current STM32F4 HAL driver was inspected at commit `1f6451c3e07728b4c830744de380e56bf5bc0026`, dated 2026-06-05, BSD-3-Clause.

Exact files:

- `Inc/stm32f4xx_ll_system.h` blob `84ea5c4d1a32511168b9bc305d26583d410cd350` exposes debug-freeze bits such as `LL_DBGMCU_APB1_GRP1_TIM2_STOP`, documented as stopping TIM2 while the core is halted.
- `Inc/stm32f4xx_hal.h` blob `f7eb847b3c1546bbe5b1c775e76f56dcd9cf9d84` exposes `__HAL_DBGMCU_FREEZE_TIM2()` and matching unfreeze macros.
- `Src/stm32f4xx_hal_pwr.c` blob `5ccde6489e2405b5b3a2347f01364fd831bec0db` contains the STM32F4 `HAL_PWR_EnterSLEEPMode()` and `HAL_PWR_EnterSTOPMode()` paths. Its current Stop-mode documentation states that HSI is selected as system clock after wake.

These are available family/HAL mechanisms only. They do not prove that the Terps Racing firmware uses these HAL calls, enters low-power modes, sets any debug-freeze bit, or uses a timer whose clock changes after wake.

Arm CMSIS documents Cortex-M DWT `CYCCNT` as a 32-bit cycle counter. That establishes a counter mechanism, not continuity through debug halt, Sleep, Stop, reclocking, or explicit reset in the team's firmware.

## Why this matters

### Paused-counter counterexample

Synthetic only:

- nominal timebase: 1 kHz;
- 20 ms running;
- 100 ms interval where the counter is paused;
- 30 ms running again.

The counter advances only 50 ticks. Dividing by the nominal 1 kHz reports 50 ms, while 150 ms of real time elapsed. A stale-data check that assumes continuous counting can therefore understate age by 100 ms.

### Reclock counterexample

Synthetic only:

- nominal reference used by software: 168 MHz;
- 50 ms counted at 168 MHz;
- next 50 ms counted at 16 MHz without changing the software conversion factor.

The counter accumulates 9.2 million ticks. Dividing by 168 MHz reports about 54.76 ms although 100 ms elapsed.

The particular 168/16 MHz values are scenario arithmetic, not a Terps Racing clock claim. The example demonstrates why a clock-source transition must be included in the timebase evidence.

## Epoch boundary

If a reachable transition cannot preserve the counter/rate continuously, a conservative source-specific design can instead invalidate old timestamps.

The portable contract models each timestamp as:

`(epoch, tick)`

A disruptive transition with reviewed invalidation increments the epoch. Any comparison between stamps from different epochs returns `cross_epoch_invalid`; it never fabricates an age.

This is a useful boundary for:
- timer reset/reinitialization;
- clock-source/rate change;
- low-power entry/exit that stops the selected counter;
- debugger modes that freeze the selected timer;
- any source-specific reconfiguration that makes old ticks incomparable.

Epoch invalidation is not automatically the right production policy. It is only one conservative method that prevents stale pre-transition timestamps from being interpreted in the new domain.

## Source-specific gate

For each potentially relevant mode or transition, bind:

- whether it is actually reachable in the 2027–28 firmware;
- whether behavior is known at the exact source revision;
- whether the selected counter continues;
- whether its effective rate is preserved;
- whether old samples are explicitly invalidated on exit when continuity is not preserved;
- exact source locations/configuration receipts.

A mode reported "unreachable" counts only when that reachability conclusion is itself team/source verified. A scenario assumption that "we never sleep" is not sufficient.

`ready_for_source_specific_freshness_review` requires all reachability/behavior claims to be team-verified and every reachable mode either:
1. preserves counter continuity and rate; or
2. has an explicit epoch invalidation boundary.

## Relationship to earlier packets

- TC-02D: modular timestamp ordering.
- TC-02E: common-domain/provenance requirement.
- TC-03B12: frequency tolerance over operating conditions.
- TC-03B13: actual timer modulus from ARR.
- TC-03B15: update-source attribution and low-word reinitialization.
- TC-03B16: whether the chosen timebase remains comparable through reachable execution-mode transitions.

Passing TC-03B16 still does not prove a deadline, WCET, control stability, or vehicle safety.

## Portable reference

`timebase_continuity_gate.py` provides:

- reviewed mode-evidence records;
- continuity versus epoch-invalidation classification;
- generic-modulus `(epoch, tick)` age comparison;
- `fresh`, `stale`, `future`, `ambiguous`, and `cross_epoch_invalid` results;
- paused-counter and rate-change simulation;
- explicit false claims for real-time continuity, scheduling deadline, independent review, vehicle acceptance, and action authority.

The reference is standard-library-only. It does not read registers or execute firmware.

## Source-specific worker packet

Prerequisites:
1. TC-03A identifies the exact board/firmware source.
2. TC-03B0 reproduces the untouched build.
3. TC-03B11–B15 identify the actual timebase, frequency path, modulus, overflow/update ownership, and reinitialization paths.

Ordered actions:
1. Search the exact firmware for `WFI`, `WFE`, HAL/LL power-entry calls, sleep-on-exit configuration, timer/CNT reset paths, clock-tree reconfiguration, DWT reset/enable writes, and DBGMCU freeze configuration.
2. Identify which of those paths can run while control/freshness timestamps are live.
3. For the chosen timebase, bind counter behavior and effective rate across every reachable transition.
4. If a transition pauses/resets/reclocks the timebase, either reject it as a continuous freshness source or add a reviewed epoch invalidation boundary.
5. Test same-epoch wrap, cross-epoch rejection, and post-transition first-sample handling in a build-only/offline fixture.
6. Keep debug-attached measurements separate from production-like timing evidence when debugger configuration can change timer behavior.
7. If Stop or other low-power modes are reachable, verify the actual post-wake clock restoration before accepting tick-to-time conversion.
8. Re-run the gate after any clock, timer, low-power, or debug-configuration change.

Stop conditions:
- mode reachability is unknown;
- a timer/debug-freeze setting is inferred instead of read from source/configuration;
- a reachable transition changes counter/rate without explicit invalidation;
- old samples can survive into a new incomparable time domain;
- validation requires unapproved flashing, vehicle actuation, or safety-system changes.

No firmware flashing, CAN traffic, HIL, dyno, track testing, scheduler mutation, or vehicle actuation is authorized.
