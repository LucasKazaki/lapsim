# TC-03B8 — stack-usage and control-path budget evidence

Status: portable build-analysis contract only. Target remains the 2027-28 Terps Racing EV torque-control project.

## Decision

Add a stack-budget gate before treating the STM32F405 instrumentation/control candidate as embedded-feasible.

The gate separates four evidence layers that are easy to conflate:

1. per-function compiler stack usage from GCC `.su` output;
2. control-path call-chain completeness, including indirect calls and recursion;
3. actual stack-region budget from the source-specific linker/startup/runtime configuration;
4. exception/preemption reserve and engineering margin supplied by reviewed project/architecture evidence rather than invented here.

A GCC `.su` file is not a whole-program stack proof. Current GCC documentation describes `-fstack-usage` as per-function output. Static entries are fixed frame sizes; `dynamic bounded` entries provide a compile-time upper bound; dynamic entries without `bounded` contain only a bounded portion and block this gate. GCC also documents `-fcallgraph-info=su`, with explicit LTO caveats, so call-graph completeness must be verified against the actual build.

## Architecture boundary

TC-03B7 established that floating-point context and preemption can alter exception stack/timing behavior. TC-03B8 therefore does not hard-code one exception-frame byte count.

ST PM0214 Rev 10 Figure 12, directly inspected in this pass, shows separate Cortex-M4 exception-frame layouts with and without floating-point storage. CMSIS-Core distinguishes the Main Stack Pointer (MSP) and Process Stack Pointer (PSP): MSP is the default after reset and is used in Handler mode, while PSP may be selected in Thread mode.

Therefore do not assume:
- the control loop uses MSP;
- PSP is configured;
- one basic-frame allowance covers nested/preempting handlers;
- the STM32F405 family's total SRAM is the stack budget.

The source-specific handoff must bind the actual linker/startup allocation and execution context.

## Public-source findings

### GCC current `-fstack-usage`

Current GCC Developer Options documentation, accessed 2026-10-02, defines each stack-usage entry as four tab-separated fields:
- source location plus function;
- mangled function name;
- number of bytes;
- qualifier(s): `static`, `dynamic`, `bounded`.

`static` is a fixed frame allocation. `dynamic bounded` supplies a compile-time upper bound. A dynamic entry without `bounded` is not a complete upper bound.

GCC also documents `-fcallgraph-info=su` and notes that LTO changes where/when callgraph information is emitted.

### Cortex-M4 stack context

CMSIS-Core documents physically separate MSP and PSP registers. MSP is the default after reset and is used for Handler mode; PSP can be selected for Thread mode.

ST PM0214 Rev 10 Figure 12 on PDF page 43 was visually inspected in this pass and shows exception-frame layouts with and without floating-point storage.

### STM32F405 memory is not the stack budget

ST documents up to 192 Kbytes SRAM for the STM32F405/415 family. That is family capacity, not the firmware stack allocation. The real linker script, startup symbols, RTOS/task model if any, globals/heaps/buffers, and MSP/PSP ownership determine the usable stack region.

## Portable contract

The retained portable reference `stack_evidence_gate.py` supports:
- current four-field GCC `.su` parsing;
- exact build/artifact/toolchain/optimization provenance;
- a gate requiring the stack-analysis artifact to match the baseline artifact before `.su` evidence is treated as source-specific;
- rejection of dynamic-unbounded stack entries;
- explicit reviewed call paths;
- rejection of unresolved indirect calls and recursion/cycles;
- MSP/PSP-specific region budgets;
- explicit reviewed exception reserve;
- explicit reviewed required margin;
- optional runtime watermark evidence only when the team requires it;
- observed headroom computation without claiming whole-program or worst-case stack proof.

The reference sums per-function frame values along explicitly reviewed paths. It does not discover call paths itself. Missing functions in the `.su` set block the path.

## Worker packet

Prerequisites:
1. TC-03A identifies the exact source/build/linker/startup files.
2. TC-03B0 reproduces the untouched build.
3. TC-03B4 proves the instrumentation-OFF patch is noninterfering.
4. TC-03B6 identifies the representative execution context.
5. TC-03B7 resolves whether FP context can affect the measured path.

Ordered actions:
1. Record exact production build commit, toolchain and optimization.
2. Produce an analysis build with GCC `-fstack-usage` using the same source/toolchain/optimization inputs.
3. Hash the resulting `.su` files and compare the analysis artifact to the untouched baseline. Preserve any drift.
4. Parse all `.su` entries on the control path; dynamic-unbounded entries block a static upper-bound claim.
5. Review the actual call graph and resolve indirect calls and recursion explicitly. If LTO changes available callgraph evidence, use a reviewed alternative.
6. Bind the active stack context (MSP or PSP) and actual linker/startup region allocation.
7. Add an exception/preemption reserve derived from the reviewed Cortex-M4/FPU/nesting model.
8. Add the team's required margin; do not invent a percentage or byte reserve here.
9. If the team requires a runtime watermark, collect it only through an authorized bench/debug path and bind it to the same artifact/context.
10. Keep MSP and PSP budgets separate if both are used.

Stop conditions:
- production toolchain/optimization unknown;
- `.su` output missing or not tied to build;
- analysis artifact drift unexplained;
- dynamic-unbounded reachable entry;
- indirect calls or recursion unresolved;
- active stack pointer/region allocation unknown;
- exception reserve or margin guessed;
- required runtime watermark missing;
- validation would require unapproved flashing or vehicle actuation.

No firmware flashing, CAN traffic, HIL, dyno, track test, watchdog/shutdown change, scheduler mutation, or vehicle actuation is authorized.
