# Racing Terps LapSim: team demo brief

**Purpose:** show what the current desktop simulator calculates, what the optional racing-line mode changes, and which team measurements are still needed before using a result for a car or course decision.

## Five-minute walkthrough

1. Launch `launch_lapsim.cmd`, select the **Prius benchmark**, and leave **Centerline (default)** selected. Run one lap. The Driver view shows the latest accepted model step while the solve runs, then plays the completed result. Read the lap time, speed, energy, lateral acceleration, and entry/exit speed boxes; point out the saved run ID. Different seam speeds mean this is one initial-condition lap, not a periodic steady-state prediction.
2. Open **Source data / model notes** and the course warning. The shipped x/y drawing and the solver's saved curvature are separate, inconsistent channels: prescribed turn is 3.657937 rad versus 6.283185 rad of map winding; integrating the saved curvature leaves a 542.633 m closure gap. The current course also has no surveyed left/right widths.
3. Select **AI racing line (experimental)**. Enter an explicitly assumed corridor, vehicle width, and safety margin. The planner tests a full and half-strength smooth offset against a newly processed geometric centerline with the same car and physics. Each path uses at most two bounded passes from the same initial car and pack state. The new modeled-path screen samples four positions per cell against the assumed clearance and requires position closure within 0.01 m. On the shipped course, the processed geometric baseline fails this check; the completed baseline/candidate times are starred diagnostics, their difference is blank, **Compare path numbers** is disabled, and no AI winner is selected. Use **Replay lap** in Driver view to inspect the labeled diagnostic runs, not to claim a lap-time gain. The ordinary centerline mode remains available and uses different curvature. If a future coherent course passes the check, speed must close within 0.005 m/s and a candidate needs a modeled gain strictly greater than 0.05 s to be selected; that margin is provisional, not a measured error bound.
4. Use **Run comparison** to run two car profiles at the same centerline settings. Read B-minus-A values and the saved IDs, then switch between A and B in Driver view's **Replay lap** menu. The profiles can be edited and saved without source-code changes, but the source-backed Terps entries remain partial working scenarios.
5. Open **Timed sessions · WIP**. Explain that a versioned car and controller, live driving against a ghost, complete session capture, and linked report are the next-stage contract; the tab deliberately cannot start a session yet. A separate Python checker can already rerun a completed saved lap's cell controls through the engineering model and report numerical differences under declared tolerances. It is not a timed-session or measured-car validation feature.

## What the optional racer actually does

It is a deterministic, offline path planner. It minimizes a geometric curvature-and-length objective within entered clearances, rejects invalid paths, and checks up to three paths with at most two physics passes each. An **eligible comparison time** requires a completed lap, a closed speed seam, and a sampled modeled-path check of usable clearance and position closure. The shipped assumed-corridor paths fail that last check despite completed model laps. The sample screen is not a continuous swept-body or surveyed cone-clearance certificate. The car and pack state still change across the lap. It does not learn from laps, steer a simulated car, see cones, or respond to traffic. The default centerline calculation does not run the planner. The Driver view is a top-down **reference-path** display with model speed and lateral acceleration, not a measured vehicle pose or a first-person camera.

## Evidence to show, and how to phrase it

- Show a saved run's input profile, solver grid, actual lap start speed, course geometry, completion status, entry/exit speeds, telemetry, and content ID. Open the AI record's linked diagnostic counterpart to inspect both completed paths without ranking them. For an engineer's follow-up, `replay_lap_record()` checks the completed v2 record's saved cell commands against the current model and reports numeric agreement separately from source/runtime differences. A record hash alone does not establish that agreement. The lap event and replay reject cells whose requested or achieved curvature differs from prescribed curvature by more than the default 1e-9 1/m tolerance; they do not verify x/y map following or cone clearance.
- Show the AI result's assumed corridor, starred baseline/candidate diagnostic times, measured sampled excess and seam gap, and blank difference. The shipped assumed ±2 m Prius baseline/full/half completed in 87.618366/87.377773/87.403816 s but exceeded the usable corridor by 0.095506/0.908195/0.501981 m. Those numbers must not be presented as a racing-line gain.
- Show the course geometry warning and the engineering handoff. The report gives the equations, Python data flow, test evidence, known mismatches, and unimplemented features.

## Data to request from the team

Ask for a surveyed centerline with left/right cone or pavement boundaries, a consistent distance/heading/curvature reconstruction, and the 2026–27 car's controlled revision of mass, wheelbase, track widths, tire force data, powertrain and battery limits, brake behavior, aero, and measured logs with stated test conditions. Those inputs matter more than a larger AI search or a learned driving policy at this stage.
